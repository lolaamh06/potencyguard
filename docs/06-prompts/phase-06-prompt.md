STEP 1. Design note first. Write docs/03-decisions/decision-0010-backend.md before coding: the endpoints, the storage layout, the trust model for public keys, the audit-log design, the SAP adapter contract, the replay/live design, every PROPOSE item with options and a recommendation, and what is out of scope. STEP 2. Storage. One SQLite database file under data/runs/ (git-ignored) with tables for: shipments (id, scenario/run label, device_id, created time, status), device keys registry (device_id, key_id, public key, registered time, registered_by, status active/revoked; append-only, revocation is a new row), ingested ledger entries (reuse the Phase 4 signed entry format unchanged), anchors, decision log entries (reuse Phase 5 format unchanged), human decisions, SAP dispatch events, and an API audit log. Append-only everywhere: no update/delete functions in the module; SQLite triggers refuse UPDATE/DELETE as in Phase 4. Status changes are new rows in a status-history table, never edits.

STEP 3. Trust model for keys. The backend never trusts a public key shipped with a ledger. A device key must be registered first through an explicit registration call (demo operator only), after which ingested entries are verified against the REGISTERED key. Ingest verifies the whole chain with verify_chain (reuse, do not reimplement) and the anchor if present. A ledger that fails verification is stored as REJECTED with the first broken index and reason, is excluded from decisions, and its shipment is set to quarantined pending review. Revoked keys: entries signed after revocation time are rejected; document the limits (the device clock is not trusted, so state plainly what "after revocation" can and cannot mean).

STEP 4. API (FastAPI, JSON only, pydantic request and response models, strict validation, sensible status codes, no stack traces in responses). At minimum:

POST /devices/register, POST /devices/{id}/revoke, GET /devices
POST /shipments, GET /shipments, GET /shipments/{id} (latest potency, trust level, verdict, chain status, latest decision, status history)
POST /shipments/{id}/ledger (ingest entries + optional anchor; verify; store; return chain status)
GET /shipments/{id}/readings (paged), GET /shipments/{id}/verify (re-verify the stored chain now)
POST /shipments/{id}/decide (runs the Phase 5 planner on the latest verified data; stores the signed decision; near-ties flagged, see Step 6)
GET /shipments/{id}/decisions, GET /approvals (open human tasks), POST /approvals/{task}/resolve (approve / override with another action / reject; who, reason of at least 10 characters, appended as a new record referencing the original, never an edit; QA identity is a plain string for now, noted as unauthenticated)
GET /audit (the API audit log, paged) and GET /provenance/{shipment_id} (source, scenario id, SAP adapter mode, software version, whether the data came from replay)
GET /health
Every state-changing call writes an API audit-log row (time, endpoint, caller label, shipment id, outcome). No authentication in this phase: document that clearly and bind the server to 127.0.0.1 by default.

STEP 5. SAP adapter. Define an SapAdapter abstract interface (one method to dispatch an event, one for an acknowledgement lookup; typed pydantic event and acknowledgement models). All SAP calls go through the interface; selection by config (backend config file) defaulting to the mock; the adapter mode is stored in the provenance. Events dispatched: only when a decision is auto-approved or a human resolves a task; the event carries the shipment, the action, the approval route and a reference to the signed decision. Neutral wording in the event description ("Event dispatched"). Do NOT guess which SAP API a real adapter would call.
