PHASE F5: PRODUCT UX OVERHAUL (MULTI-PAGE APP, PLAIN LANGUAGE, EASY NAVIGATION, LIGHT AND DARK THEME)

WHY. The user tried the F4 Control Room and found it hard to use: one dense page, jargon (CUSUM, CVaR, trust level, residual, twin, quarantine), hidden gestures (hold-to-arm is not discoverable), no pages, no light theme. It must feel like a proper, professional product that a first-time visitor can use without explanation, while keeping the 3D look. The user LIKES all the existing charts, graphs and diagrams: keep every one of them. The changes are plain language, clear pages, easy navigation, and a light theme.

READ FIRST. Read the F4 report and the dashboard/src/ tree (list it; open only what you change), docs/01-architecture/design-system.md, docs/01-architecture/frontend-vision.md section 11 (honesty rules, binding) and its amendments, and dashboard/src/controlroom/* (you will reuse its logic, store and data mapping; do not rewrite tested logic). Do not change any Python, the exporter, the replay data, or the backend.

SPEED RULES (binding). Run only targeted tests while working; run scripts/run_checks.py ONCE at the end. ONE browser review round, at most 14 screenshots at 1920x1080 and 1366x768 (covering both themes), then one fix pass on the top three issues. No soak test, no performance sweep (read the performance overlay once). Edit; do not rewrite tested logic. Keep the report under about 100 lines.

GIT RULES (absolute). NEVER run git add, git commit, git tag or git push. First run git status; if F4 is uncommitted, stop and tell me. At the end print ONE block of explicit-path git add commands (never node_modules, dist, .playwright-mcp) and ONE git commit command, with no co-author trailers. Do NOT run npm install in dashboard/; if a package is truly needed, use the F2 junction procedure (decision 0011). Prefer to need none.

HONESTY (binding; vision section 11). No external statistics. No “first”, “unique”, “novel”, “unhackable”, “tamper-proof”. No false statements: the data are sample data from a simulation; the enterprise system is a demo stand-in; actions on screen change the screen only. Do not put banners on every page; instead provide a clear “About this data” page, a small “About this data” link in the footer, and collapsed technical details. Plain wording must stay TRUE: do not soften a limit (for example “Can we trust this data? No” must stay when the checks distrust the readings). Worst-case figures stay labelled as a worst-case bound, not an estimate. Signing protects records after signing and does not stop a false sensor value; say so on the Proof page in plain words.

STEP 0. Preflight. Run git status. Confirm the Playwright tools load.

STEP 1. Information architecture. Hash routing is fine; add a router library only if you must. Pages, with a persistent top navigation that holds the logo, the page links, a Help button, the theme toggle and the Simple/Technical switch:

Home: a two-sentence explanation in plain words, a small three-step “how it works” graphic, two big buttons (“Watch the story”, “Try the demo”), and the 3D globe as a calm background.
Shipments: five cards (one per sample shipment). Each has a one-sentence plain description of what the scenario demonstrates, a status chip with icon and word (All good / Needs a person / Data not trusted / Problem found), the medicine-strength figure, and an “Open” button. Mark one card “Start here”.
Shipment (detail): a plain-language headline sentence at the top (for example “The cooling failed about 4 hours in. We recommend sending it to the nearest depot. A person needs to approve this.”). Below it: a medicine-strength gauge, the temperature chart (expected versus measured) with a simple legend, the recommendation card (action, why in 1 to 2 plain sentences, worst-case cost comparison as two labelled bars with plain captions), the approval buttons, and a “What happened” timeline in sentences. Playback controls: Play, Pause, Restart and speed (Slow, Normal, Fast), all labelled. A “Show details” expander reveals the technical panels (expected-temperature line, difference strip, alarm strip, reported versus recomputed figures, full reasons, the chain ribbon).
Decisions: the queue of items waiting for a person (from the replay data). Each item shows the recommendation, the reasons in plain words, and three clear buttons: “Approve”, “Choose a different action” (a small form with an action choice and a reason of at least 10 characters), and “Reject” (reason required). Each action opens a confirm dialog that says what will happen (“This changes this screen only. Nothing is sent anywhere.”). Keep the existing validation logic.
Proof: two plain sentences on what signed records are; a “Check the records” button that shows the recorded verification result; a “Try to change a record” button with a plain explanation, then a picker (early, middle, late) showing the recorded result of a real edit (“Record 288 was changed, so the check fails at record 288”); the truncation result with and without the end-marker, in plain words; and the honest limit: “Signing protects records after they are signed. It does not stop a wrong sensor reading from being signed.”
About this data: sample data from a simulation; the demo stand-in for the enterprise system; seed and versions in a collapsed technical list; the reference-profile figures; and what is real versus simulated, in plain words.
Story: the existing scroll story, with the new navigation bar and theme support.
Remove the hold-to-arm control and the old single Control Room page; map its shortcuts onto the new pages where they still make sense, and list only working ones in the Help dialog.

STEP 2. Plain-language layer. Create one central glossary module (dashboard/src/copy/) holding every user-facing term in two registers (Simple and Technical), a one-sentence explanation for each, and a tested lookup. Cover at least: potency, shelf life used, remaining life, MKT, expected temperature (twin), difference from expected (residual), alarm strip (CUSUM), trust level (Yes / Partly / No), each verdict (ok, thermal anomaly, sensor glitch, suspected falsification) in plain words, worst-case bound, expected loss, worst-5-percent cost (CVaR), close call, hold for review (quarantine), send to nearest depot (reroute), speed up delivery (expedite), replace shipment (re-source), carry on (continue), signed record, chain, anchor. Suggested Simple wording:

potency = “Medicine strength left”; shelf life used = “Share of its safe life already spent”
trust level = “Can we trust this data?” (Yes / Partly / No)
CVaR = “Cost in the worst 5% of cases”
quarantine = “Hold for review”; reroute = “Send to the nearest depot”
CUSUM, residual and twin are hidden in Simple mode and appear in Technical mode as “Expected temperature” and “Difference from expected”.
Every technical term that stays visible in Simple mode gets a small “?” button with a keyboard-accessible popover. The Simple/Technical switch is global, remembered, and defaults to Simple. Write all new copy at about a 9th-grade reading level: short sentences, no abbreviation without explanation. Replace jargon in headings, buttons and chart legends. The plain text must come from data fields (verdict, route, trust level, chosen action) through the glossary, never hand-typed numbers; any sentence with figures must read those figures from the exported data.

STEP 3. Guided tour and help. A first-visit, skippable tour of 5 steps with coach marks (Pick a shipment; Watch it play; Read the recommendation; Approve or choose another; Check the proof), restartable from Help. A Help dialog explains what each page is for, what each button does, and the keyboard shortcuts that work. Empty and loading states are written in plain words. Every button has a visible text label and a tooltip; there are no icon-only buttons; nothing requires a hidden gesture; risky actions use a confirm dialog.

STEP 4. Light and dark themes. Add a light token set to dashboard/src/theme/ (keep the dark set), following the design-system rules: body text at least 7:1, large text at least 4.5:1, status colours always with icon and word. Add a Vitest test that computes WCAG contrast for every text/background pair in both themes. Provide a theme toggle in the navigation (Light, Dark, System), remembered in localStorage with a safe fallback, applied before first paint to avoid a flash. The 3D globe and the charts read theme tokens and re-theme live (a pale globe with dark land dots in light mode is fine; keep it legible). The 2D fallback follows the theme.

STEP 5. Layout and polish. Larger base text (at least 16 px body, at least 14 px for the smallest label in Simple mode, at least 12 px chart text), generous spacing, cards with clear hierarchy, consistent buttons (primary, secondary, danger), visible focus rings, a responsive layout for 1366x768, 1920x1080 and a phone width (the navigation collapses to a menu), and prefers-reduced-motion honoured. Keep recording mode (?rec=1) working on the Shipment page: update its scripted sequence to the new page flow and controls, and keep it to one key to start and stop.

STEP 5B. EASY NAVIGATION (binding; it takes priority over any conflicting layout choice above).

The top navigation is on every page, always in the same place, with the current page clearly highlighted (colour plus an underline plus aria-current), and every page reachable from it in ONE click. The phone menu keeps the same order and labels.
Every page has a clear title and one line under it saying what the page is for and what to do next.
Every page except Home has a visible “Back” link, and the Shipment page has a breadcrumb (Shipments > this shipment).
A guided flow: each demo page ends with one big “Next step” button leading to the logical next page (Shipments, open a shipment, Decisions, Proof, About this data). The Home page’s “Try the demo” lands directly on Shipments with a short “Pick a shipment to begin” hint.
All charts and diagrams are kept. Each has a one-line caption saying what it shows (for example “This line is the temperature inside the box; the dotted line is what we expected”), a plain legend, and plain-word hover text. Technical charts stay under “Show details”.
No dead ends: every page offers at least one clear next action, and empty states say what to do.
Keyboard: the Tab order follows the visual order; a “Skip to content” link; the Help dialog lists the shortcuts that work.
Add a Vitest test that walks the route map and asserts that every page is reachable from the top navigation, that every page except Home has a Back link or breadcrumb, and that the Next-step chain visits all pages once with no loop.
In the report, include a “click path” table: for each page, how many clicks from Home, and what its Next-step button leads to.
